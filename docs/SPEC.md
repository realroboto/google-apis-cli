# Epic Spec: `gapi` — CLI Google unificada

> Status: ready-for-agent · Tipo: epic · Fundamentada (fatos [V] verificados contra
> docs oficiais Google; wiring do vmCODE citado por `file:line` no plano de origem
> `~/.claude/plans/liste-todos-os-mcps-greedy-pine.md`).

## Problem Statement

Hoje, para administrar as APIs Google (Google Ads, Google Tag Manager, Google
Analytics 4, Google Search Console), o operador depende de **4 servidores MCP
fragmentados**, cada um com runtime e binário próprios, auth compartilhada por
gambiarra e limitações que exigem workarounds:

- **analytics-mcp é read-only** — qualquer escrita em GA4 exige um script curl
  separado (`ga4-write.sh`).
- **O refresh token expira a cada 7 dias** (consent OAuth em *Testing mode*),
  forçando re-login manual semanal via `google-relogin.sh`.
- **GTM opera em least-privilege** (sem publish/delete/manage).
- **4 stacks** para instalar, versionar, documentar e manter em sincronia.

O operador quer uma superfície única, previsível e com escrita nativa.

## Solution

Um **repositório novo** com um **pacote npm** publicável cujo binário é **`gapi`**,
que expõe as **capacidades operacionais completas** (read+write) de Google Ads,
GTM, GA4 (Admin + Data) e Search Console, sob **um único login** que
não expira. A CLI absorve as funções de `google-relogin.sh` (auth) e
`ga4-write.sh` (escrita GA4), e depois é bakeada no vmCODE substituindo os 4 MCPs
— seguindo o mesmo padrão MCP→CLI já aplicado a context7 (`ctx7`), firecrawl
(`firecrawl`) e Bing (`bwt`).

**Desde o epic #30 (publicado como 0.2.0):** a CLI é discovery-driven. Os comandos vêm dos documentos discovery do Google em runtime (cache 24 h), com os nomes do Google (`gapi <api> <recurso>… <método>`); cada API é um arquivo de entrada de ~5 linhas. Cobertura: 47 entradas (lista em `README.md` e `skills/gapi/reference/index.md`), incluindo Merchant, Business Profile, SA360, CM360, DV360, YouTube, PageSpeed, CrUX e as APIs extras de #58.

Restrição de design do operador: **zero dependências de terceiros — apenas
Google-nativo**. Consequência: `google-auth-library` (oficial Google) como única
dependência; todo acesso às APIs via **REST cru com `fetch` nativo**; parsing de
argumentos com `node:util parseArgs` (stdlib). Sem oclif, sem commander, sem
`google-ads-api` (Opteo) — todos terceiros.

## User Stories

### Auth (login único)
1. Como operador, quero rodar `gapi auth login` uma vez e conceder todos os scopes de todas as entradas de API num único consentimento, para não gerenciar uma autenticação por API.
2. Como operador, quero que o refresh token **não expire** (OAuth client em modo produção), para não refazer login toda semana. Em **Testing** o token expira em 7 dias — relogin até publicar o app.
2b. Como **novo operador** (outra conta, outro projeto Cloud), quero `gapi auth setup` guiado para informar meu próprio OAuth client id/secret (e o `login-customer-id` opcional) gravados em `~/.config/gapi/config.json` (600), para usar a CLI sem editar arquivo à mão nem exportar env vars.
3. Como operador em container headless (sem browser), quero um fluxo `gapi auth login --manual` que imprime a URL de consentimento e aceita colar de volta a URL completa para onde o browser foi redirecionado, para autenticar sem browser local.
4. Como operador em máquina com browser, quero o fluxo loopback automático (servidor local capturando o redirect), para um login sem copiar/colar.
5. Como operador, quero que o token fique em `~/.config/gapi/credentials.json` com permissão 600, para proteger a credencial.
6. Como operador, quero que a CLI faça refresh do access token automaticamente antes de cada chamada, para nunca lidar com token expirado no meio de um comando.
7. Como operador, quero `gapi auth status` mostrando quais scopes/contas o token cobre, para diagnosticar acesso.
8. Como operador, quero `gapi auth logout` que revoga o refresh token no Google e depois apaga a credencial local, para encerrar o grant e não só o uso na máquina. Um `credentials.json` corrompido não guarda token usável: o logout o apaga sem revogar.
9. Como operador MCC (Google Ads), quero informar `login-customer-id` (via flag ou config), para operar contas gerenciadas.
10. ~~Como operador, quero informar o `developer-token` do Google Ads via env/config.~~ Removido: o `developer-token` foi descontinuado em 2026-09-09 (header ignorado pela API; o acesso passou a ser regido pelo projeto Google Cloud que possui o OAuth client). Ads não envia mais o header.

### Google Analytics 4 — Admin
11. Como operador, quero listar `accounts` e `accountSummaries`, para descobrir o que tenho acesso.
12. Como operador, quero CRUD de properties (create/get/patch/delete), para provisionar e ajustar propriedades.
13. Como operador, quero gerenciar `dataStreams` (web/app) e `measurementProtocolSecrets`, para configurar coleta.

### CLI / UX transversal
34. Como operador, quero saída JSON-first (a resposta do Google como veio, JSON indentado), `--dry-run` para ver o request antes de enviar e exit codes distintos (0 ok, 1 API, 2 auth, 3 validação, 4 discovery, 5 interno), para automação confiável.
35. Como operador, quero `gapi <api> --help` e `gapi --help` com a árvore de comandos, para descoberta.
36. Como operador, quero paginação sob demanda (sem flag, um request só; `--page-all` segue `nextPageToken`, `--page-limit` limita as páginas), para não perder dados.
37. Como operador, quero exit codes não-zero e mensagem de erro clara (com o erro REST do Google) em falha, para automação confiável.
38. Como operador, quero instalar via `npm i -g google-apis-cli` sem puxar deps pesadas, para footprint mínimo.

### Bake no vmCODE (migração dos MCPs)

## Implementation Decisions

- **Google source order (#164):** quando as fontes do Google divergem, o gapi segue esta ordem: (1) docs do produto e AIPs (https://google.aip.dev); (2) o documento discovery; (3) as client libraries oficiais do Google (python, go, node) e o `gcloud`, só onde 1 e 2 não cobrem o caso. Nenhuma fonte cobre o caso → o gapi não inventa comportamento: exit 3 com o motivo.
- **Runtime/stack:** TypeScript 7 strict, Node ESM (`type: module`), **Node ≥ 24 LTS**. Fonte em `.ts`; o Node executa `.ts` direto por **type-stripping** (estável em v24.12.0/v25.2.0, https://nodejs.org/api/typescript.html — histórico: "Type stripping is now stable.") — sem build step no dev, sem bundler. `node:util parseArgs` + `fetch` nativos. **Uma dep de runtime:** `google-auth-library` (oficial Google). Dev-deps (dev-time only): `typescript@^7` (`tsc --noEmit` = type-check, o stripping não checa), `@biomejs/biome@^2` (lint + format, substitui eslint+prettier), `@types/node`. `tsconfig` strict + `erasableSyntaxOnly` + `verbatimModuleSyntax` + `rewriteRelativeImportExtensions` — imports relativos carregam a extensão `.ts`. Package manager: **pnpm 12** (fixado via `packageManager`). **Decisão revista:** o T1 era JS puro + npm; o projeto migrou para TS7-strict + Biome + pnpm 12 (branch `chore/ts7-biome-migration`) mantendo a dep de runtime única e o runtime nativo. Publish (#7): `tsc` build → `.js` (sem `.d.ts`: nenhum `tsconfig*.json` liga `declaration`) no `prepublishOnly`; nada de `dist/` no dev. <!-- yagni: build só no publish -->
- **Bin:** `gapi` (`package.json` `"bin": { "gapi": "dist/bin/gapi.js" }`, `files: ["dist/"]`; `tsc -p tsconfig.build.json` gera `dist/` no `prepublishOnly`, #23). No repo, `node bin/gapi.ts` roda o `.ts` direto (stripping); o Catalog acha entradas `.ts` e `.js`.
- **Dispatch + entradas de API (deep-module):** cada API é uma **entrada discovery** — dados, não handlers: `{ api, discovery, scopes?, retired?, deprecated?, paid?, headers?, helpers? }` (tipo `ApiEntry` em `src/types.ts`; cada arquivo faz `satisfies ApiEntry`). Recursos e métodos vêm do documento discovery; o Catalog (`src/catalog.ts`) o normaliza em `ApiModel`, e Planner (`src/plan.ts`) + Transport (`src/transport.ts`) montam e enviam o request. `ads`, `gsc`, `indexing`, `ga4-admin`, `ga4-admin-alpha`, `ga4-data`, `ga4-data-alpha` e `gtm` são entradas (#42–#46), as 14 `merchant-*` foram adicionadas em #51 as 8 `business-*` em #52, `sa360`/`sa360-legacy` em #53, `cm360` em #54 , `dv360`/`bid-manager` em #55, `youtube`/`youtube-analytics`/`youtube-reporting` em #56 , `pagespeed`/`crux` em #57 e `bigquery-dts`, `data-manager`, `postmaster`, `site-verification`, `sheets`, `places` e `web-risk` em #58; os manifestos à mão e o strangler `legacyDoc` saíram em #47. `gsc` marca `urlTestingTools.mobileFriendlyTest.run` como retired (exit 3); `business-v4` marca 12 métodos retired e 20 deprecated; `places` marca os 5 métodos e `web-risk` 2 como `(paid)` (só marca no help, a chamada segue). `src/run.ts` (`run(argv, io)`, chamado por `bin/gapi.ts` com o io do processo) faz `parseArgs`; a **tabela de dispatch, o `--help` e a resolução de URL derivam todos das entradas por auto-descoberta** (glob de `src/apis/*.{ts,js}` — **sem registry central editado à mão**; `api` = nome do arquivo, senão o Catalog falha ao carregar). Sem framework CLI. Racional: handlers per-recurso seriam pass-throughs rasos (interface ≈ implementação — falham o deletion test); dados concentram path/paginação/auth/erro no Planner e no Transport (locality) e tornam "adicionar API = um arquivo" (leverage).
- **Módulo auth:** `OAuth2Client` do google-auth-library. Os dois fluxos usam o mesmo redirect URI `http://127.0.0.1:4600`: `login` sobe loopback só em `127.0.0.1:4600` (outro path → 404 e segue esperando; erro de listen → exit 2) e imprime a URL; `--manual` não sobe servidor e lê a URL redirecionada colada da barra de endereço (para headless; o fluxo out-of-band `urn:ietf:wg:oauth:2.0:oob` está depreciado, https://developers.google.com/identity/protocols/oauth2/resources/oob-migration). Os dois enviam `state` (32 bytes aleatórios, base64url) e PKCE S256 (`generateCodeVerifierAsync()`), e um único parser valida o redirect: `error` → exit 2 `consent failed: <error>`; `state` diferente → exit 2 `state mismatch`; sem `code` → exit 2. `access_type: 'offline'`, `prompt: 'consent'` → refresh token. `getToken({ code, codeVerifier })` troca code por tokens. **Desvio registrado:** o guia native-app recomenda porta aleatória (https://developers.google.com/identity/protocols/oauth2/native-app, "Loopback IP address"); a porta 4600 fica fixa porque o vmCODE faz port-forward dela para o login headless. Persistência em `~/.config/gapi/credentials.json` (mode 600). Refresh automático via `OAuth2Client` antes de cada request.
- **OAuth client por operador (multi-tenant).** Cada operador registra o **próprio** projeto Cloud + OAuth client Desktop; nada na CLI é atado a uma conta ou projeto. Credenciais do client resolvidas com precedência **env (`GAPI_OAUTH_CLIENT_ID`/`_SECRET`) → `~/.config/gapi/config.json` (via `gapi auth setup`, mode 600)**; sem client nos dois → exit 2 `OAuth client not configured; run gapi auth setup` (nada embutido no pacote). Resolução **lazy** (`client()` em `src/credentials.ts`, não constante de import) para captar um `auth setup` no mesmo processo. O prompt do secret é **mascarado** (eco do readline vai para um sink e `terminal: true` põe o tty em raw mode, calando também o driver) — o valor vai do stdin direto ao arquivo. Escrita de segredos centralizada em `writeSecure()` (dir 700, arquivo 600), usada pelo config e pelas credenciais.
  - **Publishing status decide a vida do refresh token** (https://developers.google.com/identity/protocols/oauth2#expiration: "a publishing status of "Testing" is issued a refresh token expiring in 7 days"): **Testing** → só emails em *Test users* (até 100), refresh token expira em **7 dias**; **In production** (botão `Publish app`) → qualquer conta, sem a expiração de 7 dias. Produção exige home page + privacy policy + terms of service (https://support.google.com/cloud/answer/15549049: "These links are required for all external production apps."). A **verificação não é pré-requisito para publicar**: sem ela, o consent dos scopes sensíveis mostra a tela "unverified app" e vale o cap de 100 usuários novos (https://support.google.com/cloud/answer/15549945); uso pessoal dispensa a verificação (https://support.google.com/cloud/answer/13464323: "If the app is for your personal use (fewer than 100 users), you and your limited number of users can continue using the app without going through verification"). Produção é o estado-alvo; Testing é suficiente para avaliar. Em produção restam gatilhos residuais (mesma página OAuth2, "Refresh token expiration": refresh token sem uso por 6 meses; limite de 100 refresh tokens por conta Google por client ID, o mais antigo invalidado sem aviso; troca de senha em token com scopes Gmail) — não aplicáveis ao uso normal desta CLI; o refresh automático (getAccessToken) reidrata transparente.
  - Onboarding passo a passo (Console, níveis de acesso Ads, customer IDs, troubleshooting): **[SETUP.md](SETUP.md)**.
- **Scopes (calculados dos documentos discovery, epic #30 D8):** não há lista de scopes à mão.
  - **Nunca pedidos:** `drive`/`drive.*` (restritos), `openid`/`email`/`profile` como scope de método, e `display-video-user-management` (Google responde `invalid_scope` para este app).
  - **Scope por método** = o primeiro scope do `scopes` do método no documento que não está no conjunto nunca-pedido (regra do `gws`). Método com `scopes` vazio numa API OAuth usa o token OAuth (YouTube `thirdPartyLinks.*`, Web Risk `projects.operations` list/delete/cancel).
  - **Tipo de auth por API:** API cujo documento não lista scope fora do nunca-pedido e cuja entrada não declara `scopes` usa API key (`crux`, `pagespeed`). Entradas sem seção `auth` no documento declaram `scopes` (`business-*`: `business.manage`).
  - **Indisponível:** em API OAuth, método cujos `scopes` são todos nunca-pedidos → help marca `(unavailable: scope not grantable)`, chamada sai exit 2, `--dry-run` funciona. Hoje: exatamente os 6 `dv360 users *`.
  - **Consent set** = união do scope por método de todas as entradas ∪ `scopes` das entradas ∪ `openid`, `email` (o `id_token` alimenta a conta em `gapi auth status`). `gapi auth login` carrega todos os documentos (pelo cache) para calculá-lo; `gapi auth status` mostra `missing` = consent − concedidos. App desktop não tem autorização incremental: API nova → novo `gapi auth login`.
  - **[V] 2026-10-14:** um consent real (Testing mode) aceitou os 32 scopes de API do conjunto aprovado + `openid`/`email` num único pedido; `cloud-platform` incluído por decisão do operador (`transferConfigs.create/patch` do BigQuery DTS aceitam só ele). Sem limite de quantidade de scopes. Missing-scope 403 traz `ACCESS_TOKEN_SCOPE_INSUFFICIENT` → exit 2 `missing scope (…); run gapi auth login`.
  - **Histórico (T1):** o conjunto original tinha 13 escopos de API das 4 APIs + Indexing (`adwords`; 7 GTM; 3 GA4; `webmasters`; `indexing`), verificados num consent real no T1; `google-relogin.sh` concedia 9 deles.
  - O quota project via header `x-goog-user-project` exige a permissão IAM `serviceusage.services.use`, não um scope OAuth [A — doc Google].
- **Planner + Transport (substituem o executor `src/rest.ts`, #37):** `plan(model, words | methodId, input, settings) → CallPlan` (puro) aplica todas as regras D5 do epic #30 — `--params` JSON com os nomes do Google, required, repeated, enum, `pattern`, `{x}` (todo char fora de `[-_.~0-9a-zA-Z]` vira percent-encoding, google/api/http.proto, #146)/`{+x}`, guard #28 (`sites/{siteUrl}` + `sites/x` → `pass the bare id: x`), `--body` só onde o método tem request — e falha com exit 3 antes de qualquer chamada de rede. `send(plan, { fetch, authorize, out })` envia; `authorize` (Credentials, `src/credentials.ts`, #41: Bearer OAuth ou `X-Goog-Api-Key`) roda antes de cada request; não-2xx → exit 1 com o corpo de erro do Google; 403 cujo detalhe `google.rpc.ErrorInfo` traz `reason` `ACCESS_TOKEN_SCOPE_INSUFFICIENT` e `domain` `googleapis.com` (AIP-193: o par (reason, domain) identifica o erro) → exit 2 `missing scope (…); run gapi auth login`. Resposta inesperada do Google (corpo 2xx que não é JSON, sessão resumable sem `Location`, upload sem progresso, resposta batch sem boundary ou com part ilegível) → exit 1 com o corpo do Google, nunca exit 5. JSON lido é estreitado por `isRecord` (`src/json.ts`, junto de `parseOrText`) + `typeof`, sem cast. `--page-all` (#38, #146; só em método com parâmetro `pageToken` de query, ou cujo schema de request tem o campo `pageToken` e o de response tem `nextPageToken` — lido do documento discovery, sem lista à mão: 13 métodos em 2026-10-15, ex.: `googleads.customers.googleAds.search`, `places.places.searchText` —, senão exit 3 `--page-all: <command> has no pageToken parameter or request field`) repete o request com `pageToken` = `nextPageToken` anterior até ele faltar ou `--page-limit` páginas (default 10), uma linha JSON compacta por página (NDJSON). Paginação pelo body reenvia o mesmo body (sem `--body`, `{}`; `--body` que não é objeto JSON → exit 3) com `pageToken` trocado (AIP-158: "all other parameters … must match the call that provided the page token"); método que devolve `nextPageToken` sem token de entrada (GA4 alpha `runReport`, `dfareporting.billingRates.list`, `tagmanager…destinations.list`, `youtube.videoCategories.list`) segue não paginável. Mídia (#48, só em método com `supportsMediaUpload`/`supportsMediaDownload`, senão exit 3): `--upload <file>` envia para `rootUrl` + `upload/` + `servicePath` + path com `uploadType` = `--upload-protocol`, também no `resumable` (como as client libraries oficiais e o guia do YouTube: `POST /upload/youtube/v3/videos?uploadType=resumable`, https://developers.google.com/youtube/v3/guides/using_resumable_upload_protocol; https://developers.google.com/workspace/drive/api/guides/manage-uploads) (default `multipart` com `--body`, senão `media`; `--upload-protocol multipart` sem `--body` e `media` com `--body` → exit 3, pois o Drive define "uploadType=media … without supplying metadata" e "uploadType=multipart … along with metadata"; `resumable` só onde discovery lista: sessão com `X-Upload-Content-Type`/`-Length`, URI do `Location`, PUT de 8 MiB com `Content-Range`, `308` = continua a partir do `Range`); `--upload-content-type` vem da extensão, senão `application/octet-stream`, e precisa casar com `mediaUpload.accept`; o arquivo é lido do disco em stream. `--output <file>` adiciona `alt=media` e, em método com `useMediaDownloadService: true`, vai para `rootUrl` + `download/` + `servicePath` + path (Discovery "Using the API": "insert /download before servicePath to avoid a redirect"; `youtube.captions.download`, `youtubereporting.media.download`, `doubleclicksearch.reports.getFile*`), grava o corpo no arquivo e imprime `{"path","bytes"}`. `--page-all`, `--upload` e `--output` não combinam. `--dry-run` imprime `{ method, url, headers, body, upload?, output?, parts? }` com `Authorization: Bearer <redacted>` ou `X-Goog-Api-Key: <redacted>` e nunca abre `credentials.json`. `--json`, `--raw`, `--limit` e args posicionais saíram.
- **Helpers (#40):** uma entrada declara `helpers` (`+nome → { summary, options, plan(ctx) }`); `run` roteia a segunda palavra com `+`, aceita `--dry-run`, `--project`, `--api-key`, `--help`, as flags de header da entrada (ex.: `ads` `--login-customer-id`) + as `options` do helper (outras flags → exit 3), e o helper monta o `CallPlan` via `plan(…)` por method id. `gapi ads +gaql "<query>" --customer <id> [--stream]`: body `{query}`; sem `--stream` imprime a primeira página de `search` como veio; `--stream` usa `searchStream` e `CallPlan.decode` concatena os `results` de todos os chunks; um chunk com chave `error` → exit 1 com esse chunk (nenhum doc do Google cobre erro no meio do stream; nunca descartado). O helper planeja `googleads.customers.googleAds.search`/`.searchStream` com `customerId` = `--customer` (#46). O endpoint de revoke recebe só o token, então revogar não precisa do client OAuth configurado. Apaga só `credentials.json` — o `config.json` sobrevive, então o próximo `auth login` não precisa de novo client. (`developer-token` descontinuado 2026-09-09 — não configurável.)

## Testing Decisions

- **Bom teste = comportamento externo, não implementação.** Testar o contrato observável da CLI (argv → efeito/saída), não internals dos módulos.
- **Seam: `run(argv, io)` (CLI in-process, `test/run.test.ts`; `test/cli.test.ts` só testa o bin com `--help`).** Testes usam entradas fixture (`io.apisDir` = `test/fixtures/apis`), cache semeado num `GAPI_CONFIG_DIR` temporário (com `credentials.json` de access token não expirado) e um `fetch` fake (`test/helpers/fetch.ts`, `Response` reais); asseveram o request exato (`--dry-run` ou chamadas gravadas), stdout, stderr e exit code. Nenhum teste bate na rede real.
- **Correção per-recurso = dados, não handlers.** `pnpm discovery:check` rebusca o documento de cada entrada e falha quando um overlay nomeia um method id ausente (CI roda semanalmente e por dispatch manual, `.github/workflows/discovery.yml`; o `prepublishOnly` também roda); o Catalog rejeita uma entrada cujo `api` difere do nome do arquivo — substitui N testes de handler.
- **Auth:** teste do refresh (token expirado → refresh chamado → novo access token usado) e da persistência/permissão 600, mockando o `OAuth2Client`. O fluxo `--manual` testado pela montagem da authUrl (`state`, challenge S256) + troca de code com o `codeVerifier` (getToken mockado), e `state` errado → exit 2 sem gravar.
- **Help (story 35):** assertar que `gapi --help` e `gapi <api> --help` listam os comandos da tabela de dispatch e saem com código 0 — teste puro, sem rede.
- **Loopback (story 4):** teste do receptor HTTP local — assertar que escuta em `127.0.0.1:4600` (linha `Listening on` impressa de `server.address()`), que `/favicon.ico` recebe 404 e o login segue esperando, que o redirect (`GET /?state=…&code=…`) troca o `code` pelo mesmo `getToken` já coberto e derruba o servidor, e que `?error=access_denied` sai 2 com `consent failed: access_denied`. Sem browser real.
- **Helpers:** `+gaql` e `+publishBatch` testados pelo `run` com `--dry-run` (request exato) e pelo fetch fake (envio); sem testes unitários de Planner, Transport ou renderers (epic #30 Testing Decisions).
- **Framework:** `node:test` (stdlib) + `assert` — coerente com "zero deps de terceiros". Um arquivo de teste por seam: `test/run.test.ts`, `test/catalog.test.ts`, `test/credentials.test.ts`, `test/cli.test.ts`. Sem frameworks extras. Fixtures: documentos discovery reais (podados com `jq`) e o `mini` feito à mão em `test/fixtures/discovery/`, com as entradas correspondentes em `test/fixtures/apis/`.
- **Prior art:** convenções do `bing-webmaster-cli` (`bwt`) — JSON-first, zero-dep; o desenho discovery-driven segue o `gws` (googleworkspace/cli): cache de discovery, nomes verbatim, `--params`, `--dry-run`, `schema`, helpers `+`, exit codes 0–5.
- **Bake (T7):** reusar `test/seed_config_test.py` do vmCODE (roster de MCPs esperado) — atualizar para 5 MCPs e presença do bin `gapi`.
